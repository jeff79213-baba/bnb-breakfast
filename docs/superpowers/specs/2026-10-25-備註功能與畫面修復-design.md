## 1. 背景與問題

### 1.1 緊急 bug（診斷報告 §2）
`renderGrid()` 的卡片模式在尾段引用 `rooms`，但 2026-08-23 改版刪掉了 `const rooms = filterRooms(tk, currentFilter);`，導致：

- 手動新增房號 → `ReferenceError: rooms is not defined` → 畫面不更新、成功提示不出現。
- 匯入 CSV/TXT（卡片形狀）→ 同上，且匯入視窗不關。
- 正式站 `https://jeff79213-baba.github.io/bnb-breakfast/` 現在就是壞的。

使用者的實際工作流包含「入住少的那天純手動輸入房號」，因此這條路徑是日常必經，不是邊緣情境。

### 1.2 需求（使用者原話）
> 「只是要加上 可備註已用餐幾人。另外 素食與蛋奶素需要有備註可寫，可用＊號，點即可看。因為有的是全家吃素或蛋奶，但是有的是一人素，其他葷。」

> 「例：兩大兩小，可能 1 大提早下來吃，另外 1 大兩小另一個時段來吃，我需要紀錄。」

兩件事，都是**自由文字備註**（使用者已明確選擇純文字，不做結構化計數）：

1. **已用餐幾人**：一房 N 人不一定同時吃完，要能記「1 大 07:30 已吃」。
2. **素食／蛋奶素細節**：現有 `eggMilk`／`vegan` 只能表達「加購 / 不加購 / 蛋奶加購 / 全素加購」，無法表達「全家素」與「只有 1 人素、其他葷」的差別。

備註需在**卡片畫面**與**匯入後的兩欄表格**都能使用（使用者確認）。

### 1.3 為何不能塞進既有 `eggMilk`／`vegan`
`core.js:20-35` 的分類判斷依賴這兩個欄位的**文字內容**：

- `isNoAdd(r)` → `r.vegan === '不加購'`
- `isAddon(r)` → `/加購/.test(r.eggMilk)` 或 `r.vegan === '加購'`
- `isHotRoom(r)` → 無 `source`／`vegan`／`eggMilk` 時才退回 `breakfastType`

一旦讓使用者在其中自由打字，「熟食／平台」與「加購」判定會跟著錯，主頁警示橫幅與備料數字連帶錯誤。因此**備註必須是獨立欄位**。

## 3. 資料設計

新增**唯一的**頂層 key：

```js
state = {
  version: 1,
  settings: { /* 不動 */ },
  rooms:    [ /* 不動 */ ],
  daily:    { /* 不動 */ },
  notes: {
    "2026-10-25": {
      "201": { eaten: "1大 07:30 已吃", veg: "1人全素，其餘葷" }
    }
  }
}
```

### 規則
1. **既有形狀完全不動**（符合報告 §0-1「不得改動資料結構」）。新增的 `notes` 是全新廂，既有程式碼沒有任何人讀它。
2. **讀寫一律經 `core.js` 純函式**（`noteGet`／`noteSet`／`migrateNote`），`app.js` 不直接操作 `state.notes`。未來要換存法只改一處。
3. **空值不落地**：`noteSet` 對空字串會刪除該欄位；該房無任何備註時刪除房號 key；該日無任何備註時刪除日期 key。因此 `notes` 不會無限膨脹。
4. **型別防護**：`loadState()` 以 `C.sanitizeNotes()` 清洗。舊裝置沒有 `notes` → 得到 `{}`。
5. **單則上限 300 字元**（存檔截斷）。表格是無換行控制的 HTML table，沒有上限會讓該列撐爆版面。
6. **孤兒備註不自動刪**：重新匯入後 `state.rooms` 換掉，某些備註會失去對應房號。渲染是逐房號畫的，孤兒天然不可見。清除只能由使用者手動按「清今日備註」（避免製造會刪資料的自動路徑，呼應報告 §0-2）。

### core.js 新增 API
```js
noteGet(notes, dateKey, roomNo, field)             // → string，缺值回 ''
noteSet(notes, dateKey, roomNo, field, value)      // → 新 notes（immutable），空值刪 key
noteCount(notes, dateKey, roomNo)                  // → 有值的備註條數（0/1/2）
migrateNote(notes, dateKey, from, to)              // → 新 notes，換房時搬移
clearNotesForDate(notes, dateKey)                  // → 新 notes，刪掉整日
sanitizeNotes(notes)                               // → 清洗後的 notes
NOTE_FIELDS  // ['eaten', 'veg']
NOTE_MAX     // 300
```

## 4. UI 設計

### 4.1 ＊ 標記
單一產生器 `noteStar(dateKey, roomNo)`：回傳一顆 ＊ 按鈕（`data-noteedit`），**永遠可見**。

| 狀態 | 外觀 |
|---|---|
| 尚無備註 | 透明底 + 淡灰框（`#ced4da`），作為**新增入口** |
| 已有備註 | 琥珀底（`#fff3bf`）+ 橙框（`#f59f00`），一眼看得出哪幾間有註記 |

> 設計修正：初版設計是「有備註才顯示 ＊」，上線後發現**全新房間因此沒有任何入口可以寫備註**。改為永遠可見，用顏色區分有無，同時保留「一眼掃出哪幾間有備註」的能力。

插入三個位置：

| 畫面 | 位置 |
|---|---|
| 卡片模式 | 房號旁（`.num` 之後） |
| 8 欄兩欄表格 | 「備註」欄尾 |
| 新訂單兩欄表格 | 「備註」欄尾 |

兩條備註都有時仍只顯示**一顆 ＊**（避免兩個觸控點擠在一起）；點開的小窗裡兩欄都看得到。

### 4.2 編輯視窗
全新 `noteModal`（`index.html`），**不塞進 `orderEditModal`**。理由：`orderEditModal` 已有 8 個欄位，平板再加兩個 textarea 會長到要捲動；且報告 §8 明誡「不要順手重構」，獨立 modal 是全新代碼路徑，既有存檔邏輯一行都不碰。

內容：
```
房號 201 備註
──────────────────────
已用餐幾人
[ textarea rows=2 ]

素食／蛋奶素備註
[ textarea rows=2 ]
[ 存檔 ]   [ 取消 ]
```

textarea 於行動裝置會自動開啟較大鍵盤，適合「1人素、其他葷」這種句子長度。

### 4.3 點擊攔截
既有兩個 row-click 切換用餐狀態的處理器需排除 `[data-noteedit]`（新訂單模式、8 欄模式、卡片模式三處），否則點 ＊ 會順便切換整間用餐狀態。

### 4.4 版本紀錄
功能選單加「📋 版本紀錄 <目前版本>」按鈕，開啟 `versionModal` 列出各版本與改動項目（最新版在最上面）。

- 版本資料集中在 `app.js` 的 `APP_VERSION` 與 `CHANGELOG` 常數。
- 選單按鈕上的版本號由 `APP_VERSION` 自動填入（啟動時設定），不需手改 HTML。
- 改版時只需動三個地方：`APP_VERSION`、`CHANGELOG`、`sw.js` 的 `CACHE_NAME`（檔案內已有註解提醒）。

## 5. 診斷報告 A 級修復

1. `renderGrid()` 卡片模式補回資料來源：在 `grid.style.gridTemplateColumns = ''` 之後加 `const rooms = filterRooms(tk, currentFilter);`（`filterRooms` 已存在，回傳已排序）。
2. 模式判斷從「看第一筆」改為「看全部」，且用 `some`：
   ```js
   function isOrderMode()      { return state.rooms.some(r => 'infant' in r); }
   function isBreakfast8Mode() { return state.rooms.some(r => 'adult' in r && !('infant' in r)); }
   ```
   選 `some` 不選 `every`：`every` 會讓「匯入 37 間 + 手動加 101」整頁掉回卡片模式、37 間看起來像消失（報告 §2 描述的最糟情境）。`some` 則保持表格，新加的房顯示空白人數，可接受。
3. `confirmImport()` 防禦性調整：`toast` 與 `closeModal('importModal')` 不可放在可能拋錯的 `render()` 之後，避免再次出現「錯誤 → 匯入視窗不關」的誤導。
4. `sw.js` `CACHE_NAME` 改版（`v22-color-stable` → `v23-notes-fix`；加入 ＊ 入口與版本紀錄後再改為 `v24-notes-entry-version`），否則平板看不到更新。

## 6. 邊界處理

| 情境 | 處理 |
|---|---|
| 現場換房（`orderSaveBtn`，`app.js:1449-1457`） | 備註與 `daily` 在同一個區塊搬移（`migrateNote`），避免以後有人只改一邊 |
| 重新匯入 | 備註依「日期＋房號」索引而保留；失去房號的備註成為孤兒，渲染時天然不可見 |
| 清除備註 | 選單「清今日備註」按鈕，只清 `notes[todayKey]` |
| 跨日 | 依 `todayKey()` 索引，天然重置。行為與既有 `daily` 一致 |
| 過長輸入 | 存檔截斷至 300 字元並 toast 提示 |

## 7. 測試

`core.js` 是 UMD、`node --test` 跑 `tests/core.test.js`，因此把備註讀寫語意放進 `core.js` 當純函式，單元測試涵蓋：

- `noteSet` 回傳新物件、不改原物件（immutability）
- 空字串／空白 → 刪除欄位與 key
- 超長字串 → 截斷至 `NOTE_MAX`
- `migrateNote` 搬移並刪除舊房號；`from === to` 為 no-op
- `migrateNote` 對不存在的來源為 no-op
- `sanitizeNotes` 對 `null`／陣列／壞形狀回 `{}`；清掉非字串與空值
- `noteCount` 計數正確

基準 30 → 約 36。DOM 層（＊ 是否出現、modal 是否開啟）目前無測試框架（報告 §12 已承認此缺口），走人工驗收清單。

## 8. 部署

- 專案無 `firebase.json` → 不跑 Firebase Hosting，僅推 GitHub，走 GitHub Pages。
- **一個部署**：`sw.js` 快取版號只改一次（`v23-notes-fix`），平板只需連網開一次就拿到 A 級修復與備註功能。
- **單一 commit**：`app.js` 同時含有 A 級修復與備註功能，兩者在同一檔案內交錯，硬拆 hunk 的風險大於收益；且兩者已由 48 支測試（含畫面層冒煙測試）一起驗證通過。若日後要回退備註功能，以 `git revert` 整個 commit 處理，不建議只回退 `app.js` 的一部分。
- 依 `AGENTS.md` §0-4：只 `git add` 明確檔案，**不可 `git add -A`**（工作區有未追蹤的 xlsx / jpg / txt 樣本）。
